# Build the oracle before the swarm

Projects that succeed with swarms of coding agents spend their preparation on mechanical verification, and very little on clever orchestration or long instruction files. Every well-documented large run rested on a near-perfect automated verifier and "dumb" coordination through git. Anthropic's C compiler used 16 agents for about $20k. Cursor's FastRender browser peaked at about 2,000 concurrent agents. OpenAI's Codex product reached about 1M lines with zero hand-written code. Each also had a short, map-style AGENTS.md, backed by repo docs and custom lints whose error messages tell the agent how to fix the problem. Controlled 2026 studies agree: context files reliably change *what agents do* but barely move *whether they succeed*, while every orchestrator that tried to be clever (shared lock files, integrator agents, Gas Town) became a bottleneck or was retired. For nami this is good news with a warning attached. Hyperbolic finite-volume (FV) methods have unusually strong oracles: manufactured-solution convergence order, conservation to round-off, exact Riemann solutions and bitwise mirror symmetry. Rust's compiler plus a strict clippy configuration enforce about half of TigerStyle. The other half (the 70-line function limit, assertion density, no recursion, bounded loops, static allocation) needs a custom `syn`-based tidy check and a `#![no_std]` kernel crate. The warning comes from the literature on LLM-written simulation code: its dominant failure is code that "runs but solves the wrong physics", so nami's oracles must be human-owned and protected from agent edits. The recommendation is to land the full guardrail layer before any framework code: pinned toolchain, lint table, tidy, one `just check` command, a dependency allow-list, CODEOWNERS plus a merge queue, Claude Code hooks, and an oracle crate. Then add a task tracker, per-agent worktrees and mutation testing before running more than a handful of agents. One caveat frames the whole effort: TigerBeetle, the origin of TigerStyle, mechanically rejects LLM-authored commits, so nami is a genuinely new test of whether TigerStyle gates make agent output trustworthy.

## Short instruction files change behaviour but barely move success

The AGENTS.md convention has won the cross-tool format war. It is plain Markdown, stewarded by the Linux Foundation's Agentic AI Foundation, read by Codex, Cursor, Copilot, Gemini CLI, Devin and roughly twenty other tools, and its site claims use in over 60k repos ([agents.md](https://agents.md/)). Nesting is standard: the file closest to the edited code wins. Codex concatenates root-to-leaf files and stops at a **32 KiB default cap** ([OpenAI Codex docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md)). Claude Code is the important exception for a mixed swarm. Since v2.1.277 it reads AGENTS.md natively, but **only when no CLAUDE.md exists**, so the portable pattern is a one-line CLAUDE.md containing `@AGENTS.md`. Anthropic's own guidance is to keep each file **under 200 lines** because "longer files consume more context and reduce adherence", and warns that with contradictory instructions "Claude may pick one arbitrarily" ([Claude Code docs: memory](https://code.claude.com/docs/en/memory)).

The evidence on what these files achieve is now fairly good, and it is sobering. The largest controlled study (ETH Zurich and LogicStar, ICLR 2026) tested Claude Code, Codex and Qwen Code on SWE-bench Lite and 138 instances from niche repos. **LLM-generated context files changed resolution by −0.5% and −2%**, neither significant, while **raising cost 20–23%**. Developer-written files gained about **+2.4%**, also not significant. Repository overviews "are not helpful": agents took as many steps to find the relevant files with an overview as without one ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v3)). The same study shows the files *are* obeyed. When a file mentioned `uv`, agents used it 1.6 times per task, against under 0.01 times when it didn't. A factorial study of 1,650 Claude Code sessions found **no detectable effect of file size, position, conflict or architecture on compliance**. The largest effect was within-session drift: each additional generated function cut compliance odds by about **5.6%** ([arXiv 2605.10039](https://arxiv.org/abs/2605.10039)). A third ablation traced failures to implementation skill (design, wiring) rather than missing repo knowledge ([arXiv 2607.27250](https://arxiv.org/abs/2607.27250)). The one dissenting result, **28.64% lower median runtime** with AGENTS.md across 124 real PRs, measured efficiency rather than success and used real developer files ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404)).

The conclusion is narrow but actionable. AGENTS.md is a channel for *commands and constraints the agent cannot infer*, not a place to explain the codebase. A catalogue of "configuration smells" across 100 popular repos found **Lint Leakage in 62%** of files (style rules a linter should enforce), Context Bloat in 42% and Skill Leakage in 35% ([arXiv 2606.15828](https://arxiv.org/abs/2606.15828)). HumanLayer sums up the practitioner view: "Never send an LLM to do a linter's job". It also estimates that frontier models follow about 150–200 instructions consistently, and that Claude Code's own system prompt already uses about 50 of them ([HumanLayer](https://www.humanlayer.dev/blog/writing-a-good-claude-md)). The drift finding argues for small tasks per session, with hooks re-checking rules, rather than longer files.

### Progressive disclosure turns the repo into the system of record

OpenAI's harness-engineering team supplies the reference layout. They first tried one big instruction file and it failed: it "crowd[s] out the task", "everything look[s] important", and it rots. Its replacement is a **~100-line AGENTS.md that acts as a table of contents**, an `ARCHITECTURE.md` describing domain layering, and an indexed `docs/`. That directory holds design docs with verification status, `exec-plans/{active,completed}/` with progress and decision logs, a tech-debt tracker, LLM-oriented reference docs for dependencies, and a `QUALITY_SCORE.md` grading each domain. Their rule of legibility is blunt: "anything it can't access in-context while running effectively doesn't exist" ([OpenAI](https://openai.com/index/harness-engineering/)). Anthropic's long-running-agent pattern adds machine-readable state. An initializer agent writes a JSON feature list in which every item starts `passes: false`, a progress file and an `init.sh` smoke test. Each coding session handles one feature and may only flip `passes`. JSON was chosen because models are less likely to tamper with it than with Markdown ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).

Spec-driven development frameworks (Spec Kit, Kiro, Tessl) formalize the same chain of constitution → spec → plan → tasks, but the evidence for them is weak. Thoughtworks found Kiro turning a small bug into "4 'user stories' with a total of 16 acceptance criteria". Spec Kit "felt like overkill" for a medium feature, and its agent ignored the research notes and duplicated existing classes ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)). nami has a better option than prose user stories. Its acceptance criteria can be *executable*: "observed order ≥ 1.9 on the isentropic vortex", "mass conserved to 10ε per step", "lake-at-rest preserved bitwise". A lightweight, spec-anchored approach fits: a short design doc per feature, with the equations, discretization, boundary conditions, CFL limit and executable acceptance tests, plus a `tasks.json` whose `passes` flags only CI may flip.

TigerStyle itself needs splitting, because TigerBeetle's TIGER_STYLE.md is a long, motivated essay ("Always motivate, always say why") ([TIGER_STYLE.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md)). It is the right *reference* document and the wrong *always-loaded* one. The right split has three tiers. A human-written Rust adaptation of TIGER_STYLE.md holds the full rationale. Ten to fifteen one-line non-negotiables go in AGENTS.md. Everything mechanically checkable is enforced by lints and tidy. Community TigerStyle agent skills exist only for Zig plus a language-agnostic variant, and **no Rust port exists** ([claudskills tiger-style](https://claudskills.com/skills/tiger-style/), [fotoetienne variant](https://skillsmp.com/creators/fotoetienne/agent-essentials/plugins-tiger-style-skills-tiger-style)). nami must therefore write down the translation decisions agents would otherwise guess at: a `usize` policy, `assert!` versus `debug_assert!`, the arena or pool pattern, and `const _: () = assert!(...)` compile-time assertions.

## Hooks enforce what instruction files can only request

Claude Code's documentation states the core principle: "an instruction like 'never edit `.env`' in CLAUDE.md or a skill is a request, not a guarantee. A `PreToolUse` hook that blocks the edit is enforcement" ([Claude Code docs: features](https://code.claude.com/docs/en/features-overview)). The harness offers a layered toolkit whose context costs differ sharply:

| Layer | Context cost | Best nami use |
|---|---|---|
| CLAUDE.md / AGENTS.md | Full text every request | Commands, non-negotiables, pointers to docs |
| `.claude/rules/*.md` with `paths:` globs | Loaded only when a matching file is read or edited | TigerStyle-Rust specifics for `crates/*/src/**`; Riemann-solver invariants; convergence-harness rules |
| Skills | Description only until used | `/add-flux-scheme`, `/add-equation-system`, `/convergence-study`, `tigerstyle-review` |
| Subagents | Isolated context | TigerStyle and assertion-density reviewer; numerics-verifier |
| Hooks | Zero unless they return output | Format, protect, gate, verify |

The docs also suggest an order of adoption. Add a CLAUDE.md line after a mistake happens twice. Write a skill once a playbook has been pasted three times. Use a subagent for noisy side tasks and a hook for "anything that must always happen" ([Claude Code docs: features](https://code.claude.com/docs/en/features-overview)). The hook surface is now broad, roughly 30 lifecycle events. They include `PreToolUse` (which can block), `PostToolUse`, `Stop`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `TeammateIdle` and `WorktreeCreate`. Handlers can be shell commands, HTTP calls, MCP tools, single-turn LLM prompts or multi-turn verifier agents. Exit code 2 blocks the action and feeds stderr back to the model. For `PreToolUse`, the most restrictive decision across all hooks wins. A blocking `Stop` hook is overridden after **8 consecutive blocks** with no tool call, so scripts must check `stop_hook_active` to avoid loops ([Claude Code hooks guide](https://code.claude.com/docs/en/hooks-guide)). The same docs warn that a file-protection hook does not stop the shell, so `permissions.deny` rules must back it up.

For nami, four hooks do most of the work. A `PostToolUse` hook on `Edit|Write` of `*.rs` runs `rustfmt` on the touched file. A `PreToolUse` hook blocks edits to oracle reference data, convergence baselines, `Cargo.lock`, `deny.toml`, the lint configuration and the TigerStyle doc. A `Stop`/`SubagentStop` hook runs the fast `just check` and returns failures. A `TaskCompleted` hook refuses completion until verification passes, which the agent-teams docs describe explicitly as a quality gate ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)). Treat all of this as defence in depth, not the last line: no controlled study yet shows hooks or skills improving success rates, and agents can bypass client-side hooks. The authoritative gates must live server-side, in CI and branch protection.

## Clippy covers half of TigerStyle; a custom tidy covers the rest

As of Rust 1.100 (stable since 2026-11-12), clippy maps well onto TigerStyle's "crash on programmer error, explicit sizes, simple control flow" rules, with three documented holes. **No lint bans recursion in general**; only `unconditional_recursion` and its relatives exist. **`too_many_lines` counts code lines only**: it skips blanks and comments, strips the braces, has a default threshold of 100, and counts closures toward their parent. It therefore cannot express TigerStyle's 70 *physical* lines. And **nothing bans heap allocation** ([too_many_lines.rs](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/functions/too_many_lines.rs), [unconditional_recursion.rs](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/unconditional_recursion.rs), [clippy lint list](https://rust-lang.github.io/rust-clippy/master/index.html)). Within those limits there is a lot to work with:

- `missing_asserts_for_indexing` flags repeated slice indexing without a prior length assert. Its rationale, that one assert lets LLVM drop all later bounds checks, is TigerStyle in miniature for stencil kernels ([source](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/missing_asserts_for_indexing.rs)).
- `arithmetic_side_effects` checks integer overflow but **ignores floats**, so it is cheap in a numerical code and lands exactly on index arithmetic.
- `float_cmp` pushes tests toward domain tolerances; its docs say "Do not use `f64::EPSILON`" as the margin ([operators](https://github.com/rust-lang/rust-clippy/blob/master/clippy_lints/src/operators/mod.rs)).
- The most agent-relevant pair is `allow_attributes` and `allow_attributes_without_reason`. Together they force every suppression to be `#[expect(lint, reason = "...")]`, which can be found with grep, counted, and errors once it goes stale. This matters because agents "fix" lints by silencing them.

The strongest configs to borrow from are uv, ruff and Bevy. uv uses `disallowed-types` with reason strings, for example banning `url::Url` in favour of its own `SafeUrl`. The reason string becomes the agent's error message, the cheapest way to encode a project rule ([uv clippy.toml](https://github.com/astral-sh/uv/blob/main/clippy.toml)). Ruff adds `iter_over_hash_type` for determinism ([ruff Cargo.toml](https://github.com/astral-sh/ruff/blob/main/Cargo.toml)). One constraint to plan around is that Cargo cannot override workspace lints per crate, so Bevy duplicates the whole table into crates that need exceptions ([bevy Cargo.toml](https://github.com/bevyengine/bevy/blob/main/Cargo.toml)). A condensed starting point for nami:

```toml
[workspace.lints.rust]
unsafe_code = "forbid"
unused_results = "warn"
unexpected_cfgs = { level = "warn", check-cfg = ["cfg(fuzzing)", "cfg(kani)"] }

[workspace.lints.clippy]
pedantic = { level = "warn", priority = -1 }
unwrap_used = "deny"
todo = "deny"
dbg_macro = "deny"
missing_assert_message = "warn"
allow_attributes = "deny"                  # force #[expect(..., reason = "...")]
allow_attributes_without_reason = "deny"
arithmetic_side_effects = "warn"           # integers only; floats ignored
as_conversions = "warn"
default_numeric_fallback = "warn"
cast_possible_truncation = "deny"
cast_sign_loss = "deny"
cast_possible_wrap = "deny"
missing_asserts_for_indexing = "warn"
float_cmp = "deny"
lossy_float_literal = "deny"
too_many_lines = "deny"                    # threshold in clippy.toml
excessive_nesting = "warn"                 # off unless threshold set
infinite_loop = "warn"
iter_over_hash_type = "deny"
wildcard_enum_match_arm = "warn"
similar_names = "allow"                    # u_l / u_r, rho_l / rho_r
many_single_char_names = "allow"           # x, y, u, v, p
```

The `clippy.toml` beside it sets `too-many-lines-threshold ≈ 60` (code lines, roughly 70 physical) and `excessive-nesting-threshold = 4`, since the default 0 means *off*. It also sets test-only allowances for unwrap and indexing, and `disallowed-methods/types/macros` with reasons for `Vec::push`, `vec!`, `format!`, `HashMap` and `Instant::now`. Several lints are known to be noisy for numerical code. `indexing_slicing` fires on every `u[i]`; prefer `chunks_exact`, fixed arrays and `missing_asserts_for_indexing` in kernels. `as_conversions` and `cast_precision_loss` fire on every count→`f64` conversion, so concentrate them in a few audited helpers behind a single `#[expect]`. `float_arithmetic` is simply unusable. The nursery lint `suboptimal_flops` suggests `mul_add`, which changes bitwise results, so decide it site by site. Do not put `#![deny(warnings)]` in source, because new toolchains add lints and break builds; pass `-D warnings` in CI and in the check command only. These noise assessments come from lint semantics and other projects' allow-lists, not measurements, and whether `disallowed-methods` catches `Vec::push` reached through `Extend` is unverified.

### A syn-based tidy test closes the gap TigerBeetle closed in Zig

TigerBeetle enforced its own style with `tidy`, a hand-written check that ran *inside the normal test suite*, so it could not be skipped. Its features were a ban list with replacement hints (`X is banned, use Y`), "leftover FIXME, remove before merge", and a function-length check that ratchets from the bottom up. It also checked operator-precedence mixing, dead files, 100-column lines and large blobs across history ([tidy.zig @ 24d92bf](https://github.com/tigerbeetle/tigerbeetle/blob/24d92bff033453dcc757adfcd9aa14655d1b1734/src/tidy.zig)). It moved out of the main tree on 2026-09-23 ([commit 2f45ef6](https://github.com/tigerbeetle/tigerbeetle/commit/2f45ef6d49084d8f6a1840eca2934bf6795b94fd)). The same file contains the uncomfortable fact for nami: a "tidy commits" check scans recent commit authors and trailers for `claude`, `codex`, `copilot`, `cursor` and others, and prints **"TigerBeetle does not allow LLM contributions."** TigerStyle's tooling ideas transfer, but its originators offer no precedent for agent-written TigerStyle.

The Rust port is a `cargo xtask tidy` built on `syn`, registered as a `#[test]`. It would check:

1. **Function length:** physical lines at most 70, closures included. nami starts from zero, so it needs no grandfathering ratchet.
2. **Assertion density:** a crate average of at least 2 asserts per function, and zero-assert functions over N lines flagged.
3. **No recursion:** a name-based call-graph cycle check. This is a heuristic that misses trait dispatch; a nightly-pinned dylint `LateLintPass` can resolve calls exactly ([trailofbits/dylint](https://github.com/trailofbits/dylint)).
4. **Bounded loops:** every `loop`/`while` needs an asserted iteration bound.
5. **`usize` in public signatures** outside indexing boundaries.
6. **Debt markers:** zero `TODO`/`FIXME`/`dbg!`.
7. **Lint evasion:** no `#[allow(`, a ratcheted `#[expect]` count, no `#[ignore]` without a reason, no `.snap.new` files, and a check that the `[workspace.lints]` table has not been weakened against a committed snapshot.

Each error should read `file:line: error: <rule>, use <replacement>`, OpenAI's "inject remediation instructions into agent context" pattern ([OpenAI](https://openai.com/index/harness-engineering/)). The guardrails themselves need tests. BeautifulRust's `check-lints.sh` compiles a fixture crate with one deliberate violation per lint and fails if a lint goes silent. Its author's single-run, model-graded benchmark showed Claude Code rising from 72 to 80/85 and Codex from 53 to 76/85 with its skills and lints. That is weak evidence, but the fixture technique is sound ([BeautifulRust](https://github.com/morganlinton/BeautifulRust)).

Static allocation is best enforced by the compiler rather than by review. Put numerical kernels in a `#![no_std]` crate with **no `extern crate alloc`**, so `Vec`, `Box` and `String` cannot be named there at all. Let the orchestration crate allocate in `Solver::init()`. In test builds, install a roughly 40-line counting `#[global_allocator]` that aborts once an `INIT_DONE` flag is set. It should abort rather than panic, since panic formatting can allocate. Then assert zero allocations across N time steps. The published crates for this are stale (`assert_no_alloc` was last released in 2021) ([rust-assert-no-alloc](https://github.com/Windfisch/rust-assert-no-alloc)). Trixi.jl's `@test_allocations` macro shows a mature numerical framework already gating hot-path allocation in CI ([TrixiTest.jl](https://raw.githubusercontent.com/trixi-framework/TrixiTest.jl/main/src/macros.jl)).

### One command, server-side gates, and a locked dependency set

Agents work best with a single command that runs every gate in fail-fast order (fmt → tidy → clippy → tests) with terse output, mirrored exactly in CI. TigerBeetle writes its CI driver in the project language rather than YAML, the same idea as `cargo xtask` ([TigerBeetle scripts](https://github.com/tigerbeetle/tigerbeetle/tree/main/src/scripts)). Use `cargo nextest run --status-level fail --final-status-level fail` plus `cargo test --doc`, since nextest skips doctests ([nexte.st](https://nexte.st/)). Pin `rust-toolchain.toml` to an exact stable such as 1.100.0 and run everything `--locked`. For supply chain, the 2026 standard set is `cargo-deny` 0.22 (advisories, licenses, bans, sources), `cargo-machete` or `cargo-shear` for unused dependencies, and `cargo-hack --each-feature`. Add `cargo-semver-checks` only once nami publishes an API ([cargo-deny](https://embarkstudios.github.io/cargo-deny/), [cargo-hack](https://github.com/taiki-e/cargo-hack)). Dependency minimalism is itself a TigerStyle value. FastRender's agents chose nearly all their own dependencies and unintentionally vendored and modified Taffy ([Simon Willison](https://simonwillison.net/2026/jan/23/fastrender)). nami should therefore use a `deny.toml` `[bans]` allow-list and put CODEOWNERS on `Cargo.toml`, `Cargo.lock`, `deny.toml`, `clippy.toml`, `rust-toolchain.toml`, `xtask/`, `justfile` and `.github/`, so agents cannot relax their own guardrails. Local pre-commit hooks (lefthook) are a convenience under 5 seconds and nothing more, because agents can run `--no-verify`.

## Mutation testing and seeded simulation catch tests that assert nothing

A swarm's tests are mostly written by the swarm, and agents fail by writing tests that pass trivially. **cargo-mutants `--in-diff`** targets that directly: it mutates only the lines a PR changed and reports mutants no test killed. The documented PR workflow is `git diff origin/main.. > pr.diff && cargo mutants --in-diff pr.diff`, with a full run on main nightly ([mutants.rs](https://mutants.rs/in-diff.html), [PR workflow](https://mutants.rs/pr-diff.html)). Requiring zero missed mutants in changed code is probably the single highest-leverage gate against vacuous agent tests. Property testing with **proptest** 1.12 fits FV invariants well: flux consistency F(U,U)=F(U), wave-speed bounds, Riemann-solver output positivity over random valid states. Commit the failure-persistence files and pin case counts so agents cannot quietly lower them. **bolero** runs a single harness under libFuzzer, AFL, Kani or plain `cargo test` ([bolero](https://github.com/camshaft/bolero)). **Kani** 0.68 can produce bounded proofs for small kernels such as index math and overflow freedom ([Kani](https://model-checking.github.io/kani/)), though its float support for flux-heavy code is unverified. **insta** snapshots need `--check`/`INSTA_UPDATE=no` in CI, because agents will otherwise run `cargo insta accept` reflexively ([insta](https://insta.rs/)). Miri, loom and shuttle earn their keep only once nami has `unsafe` or threads.

TigerStyle treats assertions as "a safety net" and TigerBeetle's VOPR simulator as "the final line of defense" ([TIGER_STYLE.md](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md)). S2's Rust deterministic simulation testing (DST) write-up gives the CI recipe: everything flows from one seed. A meta-test **reruns the same seed and compares trace logs byte for byte**, DST runs on every PR, and thousands of seeds run nightly; the approach found 17 notable issues ([S2](https://s2.dev/blog/dst)). For a PDE code, a VOPR analogue is a seeded generator of initial and boundary conditions, mesh sizes, CFL numbers and injected faults (NaN, extreme states, truncated restarts). It runs the solver under full assertions and checks invariants, and on failure prints a one-line `--seed` reproduction, which is the ideal feedback format for an agent. For performance, gate on instruction counts rather than wall-clock on shared runners. **Gungraun**, the renamed iai-callgrind, or CodSpeed's simulated CPU serve this purpose, with Bencher's statistical thresholds for alerting ([Gungraun](https://gungraun.github.io/gungraun/latest/html/index.html), [CodSpeed](https://codspeed.io/docs/benchmarks/rust), [Bencher](https://bencher.dev/docs/explanation/thresholds/)). Keep the perf gate advisory with a human acknowledgement at first, so agents don't chase regressions with micro-hacks that break TigerStyle.

## Real swarms show coordination must be dumb and the verifier near-perfect

The three best-documented runs agree on which parts matter.

**Anthropic's C compiler.** It ran 16 Opus 4.6 agents for about two weeks across nearly 2,000 sessions for **just under $20,000**, producing a roughly 100k-line Rust compiler that builds Linux 6.9 and passes about 99% of most compiler test suites. The harness was a bash `while true` loop in Docker containers. Agents claimed work by writing a lock file to `current_tasks/` and synced through a bare git upstream. There was no orchestrator agent and no inter-agent messaging. "Merge conflicts are frequent, but Claude is smart enough to figure that out." The author's central lesson is that the verifier must be "nearly perfect", or Claude "will solve the wrong problem". The test harness was written "for Claude and not for myself":
- it printed only a few lines and wrote details to files with `ERROR` on greppable lines;
- the harness, not the agent, computed aggregate statistics;
- a `--fast` mode ran a sample of 1–10% of tests, deterministic per agent.

Two failures are equally instructive. Regressions were frequent until CI was added late in the project. In the Linux-kernel phase, a single shared failing target made all agents "hit the same bug, fix that bug, and then overwrite each other's changes". The fix was to use GCC as a differential oracle with delta debugging, which split one failure into many independent ones. Code quality ended "nowhere near" an expert Rust programmer's ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)).

**Cursor's FastRender.** Cursor tried three coordination designs and documented why each early one failed. A shared file with locks collapsed: "twenty agents ran at the throughput of two or three". Optimistic concurrency made agents risk-averse. A **planner/worker/judge** hierarchy worked. Planners recursively create tasks, workers never coordinate with each other, and a judge decides whether to continue before the next cycle starts fresh. A dedicated integrator agent "created more bottlenecks than it solved" ([Cursor](https://cursor.com/blog/scaling-agents)). Planners split work into mostly non-overlapping scopes, so "most commits do not have merge conflicts", but runs cannot be steered once started ([Simon Willison](https://simonwillison.net/2026/jan/23/fastrender)). Critics reported the showcase repo failing to compile with 34 errors and red CI on main ([The Register](https://www.theregister.com/2026/01/26/cursor_opinion/)). That is a direct warning about throughput without a hard merge gate.

**OpenAI's harness engineering.** OpenAI's team grew from 3 to 7 engineers merging about 3.5 PRs per engineer per day, and used agent-to-agent review. Before automating cleanup they spent **every Friday, 20% of the week, cleaning "AI slop"**, because Codex replicates existing patterns, bad ones included. Recurring background agents now scan for deviations from "golden principles", update quality grades and open small refactor PRs that can be reviewed in under a minute ([OpenAI](https://openai.com/index/harness-engineering/)).

Heavy orchestration has a worse record. Steve Yegge's Gas Town introduced Mayor, Polecats, a Witness patrol and a Refinery merge queue. It was built in 17 days and is **now retired**, replaced by the Gas City SDK. Critics called it "vibe designed" and costly at "thousands of dollars a month" ([yegge.ai](https://yegge.ai/gastown), [Maggie Appleton](https://maggieappleton.com/gastown)). Its tracker has fared better: "Beads outlived Gas Town. I still use it every day." Beads is a Dolt-backed graph issue tracker. Hash IDs avoid merge collisions, `bd ready` lists unblocked work, `bd update --claim` claims a task atomically, and server mode supports concurrent writers ([steveyegge/beads](https://github.com/steveyegge/beads)). Claude Code's experimental **agent teams** offer a lead with teammates, a shared task list with file-lock claiming and dependency auto-unblocking, and `TaskCompleted` hooks as gates. The docs recommend 3–5 teammates and warn that "two teammates editing the same file leads to overwrites", so each must own different files ([Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)).

The empirical studies explain why file ownership and a merge queue matter. Simulated merges of 107k+ agent PRs found **27.67% had conflicts** ([arXiv 2604.03551](https://arxiv.org/abs/2604.03551)). CooperBench found two cooperating agents **about 30% less successful than solo agents**, with up to 20% of budget spent on communication that reduced conflicts but not failures ([arXiv 2601.13295](https://arxiv.org/html/2601.13295)). Semantic conflicts, where patches pass alone but fail together, are a recognized and separate risk ([arXiv 2609.25396](https://arxiv.org/pdf/2609.25396)). For nami this has three consequences. Partition work by crate and module, which suits FV well since mesh, reconstruction, Riemann solvers, time integration, boundary conditions and I/O separate naturally. Give hot shared files (core traits, `lib.rs` re-exports, the workspace manifest) a single owner. Run every PR through a **serializing merge queue that tests the rebased result**. Coordinate through the task graph and the repo, not through agent chat.

The human role in all three cases shifted from writing code to designing the harness, the specs, the architectural invariants and the oracle. Carlini wrote the initial spec, including the IR design, and the test harness, but no implementation. Anthropic's own harness post leaves open whether specialist agents beat generalists ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The useful specialists are periodic janitors (dedup, docs gardening, a code-quality critic, performance), not deeper hierarchies.

## Numerical oracles are nami's equivalent of GCC

The literature on LLM-written simulation code makes the case for oracles bluntly. LLM-PDEveloper generated new PDE modules for a JAX lattice-Boltzmann library. It passed 7–8/10 on a simple advection-diffusion solver but **0–3/10 on boundary conditions**. Its dominant failures were semantic: a dropped advection step, conditions applied to the wrong boundaries, and "spurious programs that run without error but do no meaningful computation". LLM inspector agents did not reliably catch any of these ([arXiv 2509.25194](https://arxiv.org/html/2509.25194)). A "Judge Agent" that adds pre-execution CFL and well-posedness gates and post-execution audits of conservation, monotonicity, entropy, symmetry and bounds reports silent failures falling from **42% to 1.5%**. Its single author founded the vendor and declares the conflict of interest ([arXiv 2603.25780](https://arxiv.org/html/2603.25780v1)). Even discounted, the direction is clear. "Compiles and runs" plus reviewer sign-off is not an oracle; physics-grounded checks are.

The gold standard for code verification is the method of manufactured solutions (MMS) or an exact smooth solution, combined with an **observed order of accuracy** that approaches the formal order under refinement ([Roy 2005, JCP](https://www.aoe.vt.edu/content/dam/aoe_vt_edu/people/faculty/cjroy/Publications-Articles/cjr_jcp.revise.final-accepted.pdf)). Athena++ shows how to automate it. Its linear-wave regression runs at 32 and 64 cells for each Riemann solver. It fails if the L1 error exceeds about 3.7e-8 or the error ratio exceeds **0.325**, which corresponds to an observed order of about 1.62. The thresholds are deliberately looser than the asymptotic 0.25, to tolerate coarse grids. It also fails unless left- and right-going wave errors are **exactly equal**, a bitwise symmetry oracle ([hydro_linwave.py](https://raw.githubusercontent.com/PrincetonUniversity/athena/master/tst/regression/scripts/tests/hydro/hydro_linwave.py)). Pairing an absolute-error ceiling with the ratio test matters: it catches "right order, wrong constant" bugs, such as a wrong wave speed that still converges. Run order tests only on smooth problems. Limiters drop to first order near shocks and smooth extrema, so mixed-order behaviour defeats naive refinement analysis ([Roy, grid convergence](https://www.aoe.vt.edu/content/dam/aoe_vt_edu/people/faculty/cjroy/Publications-Articles/grid-converg.submit-final.pdf)). AthenaK adds a cheap AMR check: rerun the convergence test with one corner of the mesh refined ([arXiv 2409.10383](https://arxiv.org/pdf/2409.10383)).

Major codes layer three kinds of test, and nami should tag every test by which kind it is. Athena++ prefers analytic and convergence oracles because exact comparison with stored output depends on compiler and hardware ([Athena++ wiki](https://github.com/PrincetonUniversity/athena/wiki/Regression-Testing)). Trixi.jl compares L2 and L∞ error norms against numbers written inline in the test, with `atol = 500ε` and `rtol = √ε`, and fails any test that writes to stderr ([TrixiTest.jl](https://raw.githubusercontent.com/trixi-framework/TrixiTest.jl/main/src/macros.jl)). Clawpack compares "a small set of values derived from the output" and has maintainers regenerate that data after intentional algorithm changes ([Clawpack](https://depts.washington.edu/clawpack/sampledocs/v580/regression.html)). The distinction matters for agents. Exact and convergence oracles test *correctness*. Reference-solution tests such as Shu–Osher, Brio–Wu and Orszag–Tang can only detect *change*, so an agent must never be the one to regenerate them.

| Oracle tier | Examples for nami | Agent signal strength | Who may update |
|---|---|---|---|
| Invariants on every run | Conservation to round-off (compensated sums), positivity, TVD/max-principle, entropy decay, free-stream preservation, lake-at-rest, ∇·B, CFL ≥ true max eigenvalue | Strong, cheap, no data | Nobody (code) |
| Bitwise symmetry and determinism | Mirror-symmetric data gives mirror output; 1D problem rotated to y/z axes; same-seed rerun hash | Strong, unambiguous | Nobody |
| Convergence order (smooth) | MMS with cell-averaged sources; linear waves; isentropic vortex; 3–4 resolutions, assert p_obs ≥ p_formal − δ plus absolute ceiling | Strongest correctness signal | Human (thresholds) |
| Exact solutions (discontinuous) | Exact Riemann solver for Sod/Toro tests, Burgers Rankine–Hugoniot shock speed, dam-break | Strong, one-sided rates | Human-written solver |
| Reference regression | Shu–Osher, Brio–Wu, Orszag–Tang norms and probe values | Detects change only | Human-approved commit only |

Four details tie this to the swarm. First, tests must assert that the solution *moved correctly*, for example a wave translated by c·t. A no-op solver passes steady-state and "error versus initial condition" checks trivially. That is exactly LLM-PDEveloper's spurious-program failure. Second, each boundary condition type deserves its own oracle (a reflecting wall against a doubled periodic domain, non-reflecting outflow), because BCs were the weakest agent area. Third, determinism needs a policy. CESM and FELTOR show bitwise reproducibility holds only with identical compiler, flags and FMA behaviour ([CESM-ECT](https://par.nsf.gov/servlets/purl/10304358), [FELTOR](https://arxiv.org/pdf/1807.01971)), and FLiT argues for tolerance bands around a trusted baseline across platforms ([FLiT](https://pruners.github.io/pdf/sawaya_flit_2017.pdf)). The practical tiering is bitwise hashes on one pinned CI platform, ULP-distance for reordering refactors, √ε-relative error norms across platforms, and convergence oracles everywhere. Fourth, the oracles themselves must be trusted more than the code under test. Rust has no mature FV conservation-law framework to borrow tests from (the closest crate, `corries`, is a small 1D solver) ([docs.rs corries](https://docs.rs/crate/corries/0.6.0)). So humans should write, or carefully cross-check, the exact Riemann solver and manufactured solutions. Ideally they are checked against an independent implementation such as Clawpack's, which then also serves as a differential oracle in the same role GCC played for the compiler. Some specifics in this section, notably Rust's FMA contraction behaviour, libm variance across platforms, and the published Toro test parameters, come from domain knowledge rather than sources fetched for this report. Verify them when writing the oracle crate.

## Recommended tooling stack for nami, in priority order

The ordering follows one principle from the evidence: **the guardrails and oracles must exist before the code they guard**, because agents replicate whatever patterns they find first ([OpenAI](https://openai.com/index/harness-engineering/)), and the C compiler suffered regressions until CI arrived late ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)).

| Priority | Item | Concrete choice |
|---|---|---|
| **P0: before any framework code** | Context files | Root `AGENTS.md` of 60–150 lines (commands, TigerStyle non-negotiables, numerical invariants, docs map); `CLAUDE.md` = `@AGENTS.md`; nested AGENTS.md per crate only where rules differ |
| P0 | Docs as system of record | `ARCHITECTURE.md` (crate layering and allowed dependency direction); `docs/TIGER_STYLE.md` (human-written Rust adaptation); `docs/design/` ADRs with status; `docs/exec-plans/{active,completed}/`; `docs/glossary.md`; `docs/references/` |
| P0 | Toolchain and format | `rust-toolchain.toml` pinned to an exact stable (for example 1.100.0) with rustfmt and clippy; `rustfmt.toml max_width = 100`; `rust-version` = pinned toolchain |
| P0 | Lints | `[workspace.lints]` as sketched above; `clippy.toml` thresholds plus `disallowed-*` with reasons; `-D warnings` only in CI and check command |
| P0 | Tidy | `cargo xtask tidy` (syn) as a `#[test]`: 70 physical lines, assertion density ≥ 2, recursion cycles, loop bounds, `usize` policy, bans with replacements, zero TODO, `#[expect]` ratchet, lint-table snapshot; lint fixture crate in BeautifulRust style |
| P0 | Static allocation | `#![no_std]` kernel crate without `alloc`; counting global allocator that aborts after init; zero-allocation-per-step test |
| P0 | Oracle crate | Human-written exact Riemann solver, manufactured solutions, convergence harness (p_obs + absolute ceiling), invariant checkers; terse output with `ERROR` lines; deterministic `--fast` sampling |
| P0 | Single command | `just check` (fmt → tidy → clippy → nextest → doctests), under about 60 s, identical in CI |
| P0 | Server-side gates | Branch ruleset on `main`, required checks, **merge queue** testing the rebased result, linear history; CODEOWNERS on guardrail files, oracle data and `deny.toml` |
| P0 | Supply chain | `cargo deny` with `[bans]` allow-list, `multiple-versions = "deny"`, unknown registries and git denied; `--locked` everywhere |
| P0 | Claude Code harness | Hooks: PostToolUse rustfmt, PreToolUse protect list (backed by `permissions.deny`), Stop/SubagentStop `just check`, TaskCompleted verification gate; path-scoped `.claude/rules/` for kernels, solvers and tests |
| **P1: before more than about 3 parallel agents** | Isolation | One git worktree or container per agent; agents rebase and resolve their own conflicts; no dedicated integrator agent |
| P1 | Task tracking | Beads (atomic claim, dependency graph, hash IDs), or the C compiler's `current_tasks/` lock files; per-plan `tasks.json` with `passes` flags that only CI flips |
| P1 | Test-quality gates | `cargo mutants --in-diff` with zero surviving mutants in changed code; proptest with committed regressions and pinned case counts; insta with `--check`; bitwise determinism meta-test |
| P1 | Skills and subagents | `/add-flux-scheme`, `/add-equation-system`, `/convergence-study`; TigerStyle reviewer and numerics-verifier subagents |
| P1 | Performance | Gungraun instruction-count benchmarks for flux, reconstruction and one full step, advisory with human acknowledgement |
| **P2: when scaling the swarm** | Orchestration | Planner/worker/judge cycle with fresh restarts; concurrency capped at the number of independent failing oracles |
| P2 | Janitors | Recurring dedup/refactor, docs gardening, quality-score updates, numerical-analyst critic |
| P2 | Deep verification | Nightly full mutants, bolero fuzzing of flux/limiter/wave-speed with NaN and extreme states, VOPR-style seeded PDE simulation, Kani proofs of index math, differential runs against Clawpack |
| P2 | Spend control | Per-run token and dollar budgets, bounded run duration, sampled human audits of merged numerics |

## Open decisions for the user

These choices change the tooling and cannot be settled by the evidence alone.

| Decision | Options and trade-off |
|---|---|
| Integer width policy | TigerStyle prefers `u32` over `usize`, but Rust indexes with `usize`. Options are `u32` newtypes (`CellIndex`) converted at the indexing boundary, or `usize` everywhere with overflow asserts. This determines the tidy rule and `arithmetic_side_effects` allow-list. |
| Assertions in release builds | TigerBeetle keeps assertions on in production. Options are `assert!` everywhere (safety, small cost) or `debug_assert!` in inner kernels, plus a profile with `overflow-checks = true` for tests. |
| Floating-point determinism contract | Bitwise on one pinned platform only, or across platforms? Whether to allow `mul_add`/FMA, which libm to route transcendentals through, and whether `target-cpu=native` is banned in test builds. |
| Indexing in kernels | Allow `indexing_slicing` in kernel modules with `missing_asserts_for_indexing`, or force iterator and `chunks_exact` style everywhere. |
| Recursion check fidelity | A cheap `syn` name-based heuristic (blind to trait dispatch) versus a dylint lint with exact resolution but a nightly toolchain to maintain. |
| Who writes the oracles | Human-written exact solvers and manufactured solutions (slower, trustworthy), or agent-written ones gated by differential comparison against Clawpack or Toro reference codes. |
| Orchestrator | A bash loop with containers (the C compiler model, simplest), Claude Code agent teams (experimental, no nesting, 3–5 teammates), or Gas City / custom (more capacity, more complexity). A single vendor or a mixed Codex and Claude swarm (AGENTS.md portability then matters). |
| Tracker | Beads (Dolt dependency, richer graph) versus plain lock files and `tasks.json` in git (zero dependencies, in keeping with TigerStyle). |
| Dependency budget | Literal "zero dependencies" beyond std, or an allow-list that admits dev-only crates (proptest, insta, bolero) and nothing in the runtime path. |
| Merge-gate strictness | OpenAI-style minimal gates with flaky tests rerun for throughput, or a strict queue where every gate must pass. Throughput limits of a serialized Rust CI gate at swarm scale are unmeasured. |
| Human review model | Which artefacts require human approval (ADRs, oracle thresholds, reference data, guardrail files) and what sampling rate of merged numerics gets audited. |
| Budget envelope | The only well-documented anchor is about $20k for 16 agents over two weeks on a well-oracled Rust project. No primary cost data exists for larger swarms. |

## Conclusion

The evidence reframes "preparing a repo for an agent swarm" as building a numerical-analysis lab before hiring the analysts. The parts that matter, oracles, lints with remediation messages, write-protected reference data and a merge queue, are the same ones a careful human team would want. The swarm only raises the cost of skipping them, because agents faithfully copy whatever they find and confidently report green tests that check nothing. nami holds two unusual advantages. Its domain has mathematically exact oracles that most software lacks, and its language makes the compiler a first-line verifier. Its main risk is the reverse of the showcase failures: not code that fails to compile, but plausible solvers with a dropped term, a misplaced boundary condition or a no-op update that still pass weak tests.

Two things remain unknown and worth measuring as nami proceeds. No one has published a swarm-built scientific code, and nothing yet shows that mechanical TigerStyle gates make agent output trustworthy; TigerBeetle chose to ban the agents instead. Treating nami as that experiment would be valuable in itself: track surviving mutants, oracle failures caught per merged PR, `#[expect]` counts and janitor-PR volume from day one. That would turn the project's tooling decisions into evidence, not just a bet.
